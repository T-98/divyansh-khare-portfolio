Voice AI Systems Voice Claims Agent · Solo Build 16 min read Aug 2026

The Model Can Ask for Claims. It Cannot Say Whose.

A phone number that answers, verifies who is calling, reads back a claim status, answers policy questions from a knowledge base, and hands off to a human when it should. The interesting part is not that a model can hold that conversation. It is that nothing the model says is ever allowed to become authorization.

A caller says their phone number. The transcriber hears "4 1 5, 5 5 5, 1 0 0 9", or it hears "four one five triple five ten oh nine", or it hears the first six digits and then a pause it interprets as the end of a sentence. Meanwhile a model in the middle of the loop is perfectly capable of emitting a JSON tool call for a customer who is not on the line.

So the architecture has one governing rule, and every other decision in the build is a corollary of it:

An agent node is the only place a model runs. A tool node is the only place facts get written. The model proposes; the code disposes.

Vapi owns the phone, the speech-to-text and the text-to-speech, and talks to my server as though it were OpenAI: one POST /chat/completions per transcript update. FastAPI turns that into one caller turn and runs a LangGraph state machine. The graph is an authentication loop, then a router that triages each turn to a claims agent, an FAQ agent, a sign-off or an escalation. Claims data is read from Supabase, policy answers are retrieved from an embedded corpus, and when the call ends a webhook fires one gpt-5 pass over the saved state and upserts a single Airtable row.

You can call the agent yourself — the number and a test identity are on the front page.

Five scenarios. Thirty-three checks. Zero failures.

Both failure modes are worse than useless.

Build 02 / 04

Auth, claims and FAQ are the identical shape: an agent node that may speak or may propose a tool call, and a tool node that runs no model, executes what was proposed in plain Python, and is the only place a fact enters state. The agent node never reaches the database. The tool node never speaks. Escalation is the same shape with the tool half deleted, because it has nothing to look up — it talks, and a human does the rest.

That split is what makes the security property checkable rather than aspirational. The grant — authenticated, customer_id, customer_name — is written in auth_tool_node from parsed tool JSON, never from anything the model said in a sentence.

No tool takes a customer_id the model can fill in

Two different mechanisms enforce that, and knowing which is which matters:

  • Auth: the parameter does not exist. lookup_customer produces a customer_id; nothing accepts one. There is no string the model could emit that names a customer.
  • Claims: the parameter has to exist, because the query needs the id. So it exists and is marked InjectedToolArg, which removes it from the schema sent to the model — fetch_claims ships with an empty properties object, verified by dumping it. The tool node fills it from state, spread after the model's arguments, so state wins even for a key the model was never shown.
  • Same treatment on select_claim, for a different reason. The caller's own claims are injected so a claim_id resolves against that list only. A borrowed id and a hallucinated one are indistinguishable, and both come back unknown_claim.
  • FAQ: no boundary, because there is nothing to protect. search_knowledge_base takes a query and nothing else, and its corpus is identical for every caller. The absence of an injected arg there is a consequence of the data, not an oversight.

None of that is worth much as an assertion, so it is a test: test_fetch_claims_ignores_a_model_supplied_customer_id fabricates a tool call naming another account and checks the answer is still the caller's.

Rules first, model on a tie

The router is deliberately not a model call in the common case. A clean keyword hit on one side and nothing on the other is a decision, made in Python, for free. The model is the tie-breaker: it sees the last five messages and decides when the utterance is genuinely contested.

Which is exactly the fix for the routing bug I did have. "Where do I mail documents" went to the claim agent, because "document" is on the claim keyword list and nothing on the FAQ list matched — a clean single-sided match, no model call, wrong node. The fix was not to remove "document" from the claim list, because "did you get my documents" is genuinely a claim question. It was to make that utterance contested so it reaches the model fallback. Same words, different things; the decision belongs to the layer that can see the conversation.

Read on the caller's clock. Write once, after they hang up.

Integrations 03 / 04

The write-back timing is the one people ask about. The graph reaches END on every single turn — that is what a turn is. So an Airtable write triggered on graph completion would produce a row per turn, not a row per call. The record is driven by Vapi's end-of-call webhook instead, reads the last Postgres snapshot rather than live state, and lands as a single PATCH upserted on call_id. Vapi retries webhooks; idempotency is not optional.

The last line of that section is the one I would defend hardest. VAPI_SECRET originally guarded /chat/completions — but Vapi only sends its server secret to the webhook URL. It had never been set, which is the only reason nothing broke; setting it would have 401'd every caller turn. A control that is inert when unset and catastrophic when set is worse than no control at all. It moved to /webhook, which is the endpoint that matters anyway, since that payload is what writes the record.

What the phone taught me

Every complication in auth.py is a scar. Here are the ones worth the telling.

A caller pausing mid-number got hung up on

Vapi re-sends a growing transcript every time endpointing thinks you paused — "Yeah. My number is", then "Yeah. My number is 4 1 5", then the whole thing. I was counting each as a fresh turn, so one phone number burned five turns and tripped a ceiling on the request that finally carried the complete utterance. They are cumulative, not fragments, so a prefix comparison collapses them.

But not counting them was only half the job. The graph was still running on each re-send: appending messages the caller never heard, routing on half a sentence, sometimes firing a tool. One utterance, two graph runs, the caller hearing the two spliced together. The fragment cannot simply be skipped, because it arrives first and nothing in the payload says which request is last. So every request waits DEBOUNCE_SECONDS = 0.4 before doing anything; if a newer request for the same call arrives meanwhile, this one has been superseded and returns an empty reply without touching the graph. The wait happens before the per-call lock, or a waiting request would hold the lock through its own wait and nothing could ever supersede it. Cost: 400 ms per turn. Saving: the one-to-two wasted graph runs it replaces — 6.2 s and 10.3 s of model latency on the call I measured it against.

Two requests for one call ran at once

I had written down that this was impossible, reasoning that Vapi waits to hear turn N before sending N+1. It does not. Both read state before either wrote, and the caller heard the same question twice in different words. One asyncio.Lock per call_id.

Tool turns cost two model calls

The second one only read a status and recited a sentence that was already in the prompt — a network round trip for a dictionary lookup. Moving it into code halved those turns and stopped the readback drifting; the model had started dropping the commas out of the phone number.

And the first fix was in the wrong place. I put the scripted line in auth_tool_node, because it was already holding the parsed result. That made two nodes able to answer the caller, needed a conditional edge to work out which one had, and forced the tool node to hand-merge its own pending update just to guess whether a ceiling was about to fire. The behaviour was right and the seams were wrong — and I could tell, because explaining who spoke when took several attempts. Moving the decision into auth_agent_node as a second early return gave the same one model call per turn, one node that speaks, and deleted the conditional edge entirely.

My absolute ceiling was 8 turns, and a messy real verification is 8 turns

It fired on someone who had cooperated the whole way. Raised to 15: it is the last resort, not the defence. The related bug is subtler — a caller who simply refuses never fails. auth_attempts only moves on a real failed lookup, so eight turns of "I'm not giving you my number" sat at attempts=0 with no exit. A cap on failures cannot bound someone who never gives you anything to fail on, hence a separate stall counter and the model judging refusal.

The FAQ agent refused questions it could answer

It abstained on "what's my deductible" — a topic the corpus answers at 0.64 similarity — with no retrieval call logged at all. One earlier empty search sitting in the transcript had taught it that questions like this come back empty, so it stopped searching. The rule that fixed it is the one worth stating: an abstention has to be grounded in a search too. Refusing without looking is a guess in the other direction, and it is the guess that loses answerable questions.

The same bug bit twice, from opposite sides of a boundary

Vapi hangs up by matching an end-call phrase as a substring of what the assistant says. First I picked a sign-off that opened with the greeting's words, configured as two comma-split entries — so every call hung up 8.7 seconds in, before the caller had said anything. I fixed the code and added an import-time guard. Then fixing the dashboard merged the two broken halves back into the old phrase, so the list held something nothing says any more and the new closer was never added: the sign-off played and the line stayed open.

Both halves looked fine from where I was standing — the first from the logs, because the greeting went out and the next request simply never came; the second from the code, because the string was right in the repo. The fix that matters is neither patch. It is the ends_call field now on every turn log, which says which of our phrases we actually spoke.

The transcript is not evidence. I diagnosed the first bug from Vapi's word-level confidence scores and got it wrong — they are truncated in every payload. Logging what we actually fed the graph was worth more than any of it.

One process. One lock per call. Everything else async.

04  Technical discussion System design

A single worker is load-bearing

Two workers means two checkpointers — turn 2 lands in a process that never saw turn 1.

One asyncio.Lock per call_id

Turns queue within a call. Calls run alongside each other.

call B turn 1→ turn 2→ turn 3 concurrent

Async handler, blocking nodes

An awaited async invoke offloads to a thread executor. The synchronous call would freeze every other caller. Audit writes are never awaited.

Technical discussion 04 / 04

The in-process checkpointer is the honest limitation of the build, and it is worth being precise about why. thread_id is a conversation label — nothing to do with CPU threads, nothing spawned or torn down. It is a key in a dictionary, and the first write creates the entry. One notepad per call, not per turn: I watched messages grow 4 → 6 → 10 across three turns of one call, same entry.

The notepad lives in that checkpointer instance, not in the thread_id. Rebuild the graph and you get an empty shelf with the same labels — every turn looks like a new call. Two worker processes are two shelves, and turn 2 cannot find turn 1. Hence --workers 1, and hence Redis as the production answer. Worth noting what Redis changes and what it does not: it moves where the dictionary lives, not why it needs keys. You would still have to find this call among thousands.

It is also why the deploy target is Railway rather than something serverless. Cloudflare Workers, Lambda and Cloud Run scaled to zero are stateless per-request isolates — turn 2 lands somewhere with no memory of turn 1, which is the same failure as --workers 2. Render's free tier spins down after 15 minutes and cold-starts in about 50 seconds, and Vapi's server timeout is 20, so the first call after a quiet period fails outright. Railway does not sleep services. That is the one property that matters.

Gaps, owned first

A build is defined as much by what it refuses to claim. These are the ones I would raise before anyone found them.

Multi-intent is dropped, not parked
"Is my claim approved, and what's my deductible" gets the first ask answered and the second forgotten. I built a followup field to detect and store it, then deleted it because nothing ever read it — better an honest gap than a field that looks implemented.
The handoff keywords over-match
"Is this a robot or a real person?" matches real person and escalates, though it is a question about me. The shortcut trades that false-positive tail for skipping a model call on every genuine handoff.
The attempt budget is per call
A redial gets three more. Cross-call rate limiting is production work.
Needing a second factor confirms an account exists
Account enumeration, unavoidable alongside readback-and-confirm. Accepted knowingly.
The readback confirmation costs a stall point
By turn 2 the last message is the tool node's own trailing reply, not a tool result, so a perfectly on-script "yes" reads as "nothing usable arrived" and stall goes 0→1. Harmless — the budget is 5 and a normal run never passes 2 — but real. Found in a live trace, not in the code.
A crash loses in-flight calls
Snapshots are forensics. Rehydration is not built.
"Do you tow cars" abstains rather than answering
The roadside section says this line does not dispatch roadside, which is the answer — but the query scores 0.28, under the floor, so the caller gets the generic refusal. Correct, not ideal. Lowering the floor to catch it also catches "hello how are you today" at 0.24.

What I would defend

Voice is the format that punishes an architecture fastest. There is no loading spinner to hide behind, no form validation to lean on, no second chance to re-read the sentence. Every decision either survives contact with somebody talking or it does not.

What survived was the boring rule. The model is very good at understanding that a caller pausing mid-sentence is still mid-sentence, and very good at working out that "the one from last month" means a specific claim. It is not the thing that should decide whose claim it is allowed to read. Give it the first job, take the second away structurally, and the failure modes left over are the ordinary kind — the ones you can measure, log, and fix on a Tuesday.
